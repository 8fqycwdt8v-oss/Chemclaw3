# The storm — mock-driven stress, chaos and adversarial pass, 2026-08-04

Harness: `chemclaw.cli.live_storm` + `chemclaw.cli.mock_llm` + `chemclaw.cli.storm_behaviours`
(`make live-storm`). Stack: PostgreSQL 16 + pgvector 0.8.6, Temporal Server 1.31.2, six connectors,
four Temporal workers, the front door, and an HTTP mock of the **Responses** API in place of a
model. Zero LLM calls; the mock reports how many requests it served, which is how the run *proves*
that rather than asserting it.

**Why a mock rather than a model.** Volume is the lesser reason. The sharper one is that a real
model will not, on request, emit an empty function name, a truncated argument document, forty
parallel calls, or a turn with no prose — and every one of those has been a live defect in this
system. The mock makes them a parameter. It is an HTTP mock rather than an injected chat client on
purpose: the streaming assembler, the middleware stack, budget admission, the audit sink and the
session store all sit between the socket and the agent, and the in-process scripted client in
`tests/` bypasses every one of them.

---

## What it found in the product

### 1. The `openai_compatible` streaming path announced ten tool calls for one call

`api/runner_trace.py` reassembles a streamed function call. It treated a content carrying **both** a
name and non-empty arguments as a complete, non-streamed call:

```python
if name and arguments:   # "the streamed shape never looks like this"
```

That comment was true of Anthropic and false of the OpenAI Responses API, which puts the name on
*every* `response.function_call_arguments.delta`. So each fragment matched, overwrote the fragments
before it, and flushed.

| behaviour | before | after |
| --- | --- | --- |
| `c-whole` (1 call, arguments whole) | 1 announced / 1 returned | 1 / 1 |
| `c-fragmented` (1 call, 8 fragments) | **10 / 1** | 1 / 1 |
| `c-parallel` (6 calls × 3 fragments) | **18 / 6** | 6 / 6 |

The first of those ten events carried `{"t` as if it were the whole argument document. The fix
tests the argument's *type* rather than the presence of a name — a name says nothing about
completeness, only the arguments do — and a string is always accumulated and finished by
`_arguments_complete`.

**The `openai_compatible` seam had never been exercised live.** It is the seam the target
deployment uses (F0: an internal OpenAI-compatible endpoint), so this is a defect that CI, the
type checker and 3,000 tests all had no way to see.

### 2. A SIGKILLed connector worker costs 600 s before its job resumes

Chaos family, measured against a live broker:

> at kill: **RUNNING** · after restart: **COMPLETED 583 s later** (heartbeat timeout is 600 s) ·
> `job_records` rows: 1

Durability holds — the job finishes, the record is written, nothing is lost. The *latency* is the
finding, and it had never been measured. The activity stays `Started` against a worker identity
that no longer exists, pinned at `species 1/5: c1ccccc1`, and Temporal reschedules it only when
`xtb_job_heartbeat_timeout_seconds` expires.

The coupling behind it is the part worth acting on. That one setting must be longer than the
slowest legitimate gap between heartbeats — a CREST search, whose own manifest says its cost "is
not bounded by the input's size" — **and** it is the only signal that detects a dead worker. So
every calc job pays the CREST-sized detection window, including the ones that heartbeat every few
seconds. On OpenShift, where pod eviction is routine, that is ten minutes of dead time per
eviction. Recorded in `docs/planning/BACKLOG.md`; a per-job value is a config-surface decision, not
a diff to slip in beside a test pass.

### 3. SCALE-3, open since July, answered — at cap 16, and the first answer was an artefact

The previous sweep varied *offered* load against a fixed `service_max_concurrent_turns = 8`, which
measures shedding. The cap is read once at startup into a semaphore, so the only honest way to
sweep it is to restart the front door at each value — which `family_a_admission` now does, holding
offered load at 48 concurrent turns and taking **three samples per cap**, each behind its own
restart.

| cap | accepted | p50 s | **answered/s** (median of 3) | within-cap spread |
| ---: | ---: | ---: | ---: | ---: |
| 2 | 6 | 5.9 | **0.84** | 3 % |
| 4 | 9 | 6.6 | **1.11** | 9 % |
| 8 | 16 | 8.2 | **1.48** | 7 % |
| 16 | 23 | 11.7 | **1.70** | 7 % |
| 32 | 32 | 16.8 | **1.80** | 4 % |

Against the sweep's own measured 9 % noise floor: 8 → 16 buys **+15 %**, and 16 → 32 buys **+5.9 %**,
which is inside the noise. **The knee is at cap 16.** Raising the shipped default from 8 to 16 is a
real 15 % goodput gain for a 43 % p50 increase (8.2 s → 11.7 s) — an operator's trade-off, now
with both numbers on it. Going to 32 buys nothing this sweep can distinguish and costs another 44 %
of latency.

**The first answer to this was cap 8, and it was an artefact.** Three single-sample runs put the
8 → 16 step at +6.3 %, +3.9 % and +13.5 % — straddling the fixed 10 % threshold the first version
used — so the same stack answered "the knee is at 8" twice and "no knee in range" once. That
threshold was chosen in advance, and the docstring justifying it asserted the run-to-run spread was
"a few percent" with nothing having measured it.

That is precisely D-2026-08-04-a-plateau-needs-the-noise-you-measured-it-with — *"a plateau test
that supplied its own noise would reproduce the error with a tool's authority behind it"* — an ADR
written the day before, in this repository, about this class of mistake. Repeating it inside a
harness whose entire purpose is to stop measurements from lying is worth recording plainly.

The fix is the ADR's own rule: the knee is judged against the spread the sweep measured, and a
sweep too noisy to read one says so (`_MAX_READABLE_NOISE`) rather than reporting a number.

**And the correction introduced its own way to be confidently wrong.** A noise floor makes the knee
fire *sooner*, not later — "this step is smaller than the spread" is a statement about the
measurement — so at a large enough spread every step qualifies and the knee lands on the smallest
cap. A sweep that could see nothing would have named cap 2 with confidence. Found by writing the
test for the opposite behaviour and watching it fail, which is the only reason it is not still
there.

### 4. Everything else that held

Twenty-seven mechanical checks across eight families. The ones worth naming because they had never
been asked of a live stack:

- **A client that disconnects mid-turn frees its session in 0.2 s** (lease is 60 s). This is the
  CHAOS-1 regression: the 2026-07 load test measured **63 seconds**, because nothing released the
  claim when the generator closed. `api/routes/turns.py` now releases both the in-process slot and
  the durable claim in the stream's `finally`.
- **Postgres restarted under load**: 22 of 24 in-flight turns survived, and a fresh turn answered
  1.7 s after the bounce — the pool reconnects without the front door being restarted.
- **A durable launch with no broker at all** reaches the asker as `tool_failed` naming the tool and
  the reason, rather than hanging or answering anyway.
- **Twelve simultaneous identical launches produce exactly one `job_records` row** — D-011 under
  contention.
- **Unicode** (`咖啡因 · Ω · 🧪 · ünïcødé`) read back byte-exact out of `session_messages`, and an
  **injection string** asking for `DROP TABLE audit_events` left the row count rising.
- The whole adversarial family: a truncated argument document, LOAD-1's own wrong-argument shape,
  an unknown tool, an empty function name (STREAM-1), a 100 KB argument, forty parallel calls, a
  turn with no prose, and an upstream 500 — each **reported** rather than swallowed.

## What it found in the harness, which is most of it

Five of the eight defects this pass turned up were in the measurement. That is not an accident of
this run; it is what happens the first time a signal is used. A check that has never been wrong has
usually never been used.

### The storm claimed eight families and ran six — and then claimed all eight and ran seven

`run_storm` wired A, B, C, D, F and G. **E (chaos) and H (data edges) were planned and never
implemented**, and six behaviours — `a-retrieval`, `d-status`, `f-slow`, `h-bad-smiles`,
`h-injection`, `h-unicode` — were defined and asserted by nothing. The report printed
**"17/17 checks passed"**, which is true of what ran and silent about what did not.

A pass count cannot say anything about coverage. `FAMILIES` now declares the planned set, the
report prints planned-versus-ran and names any family that produced nothing, and the exit code
depends on coverage as well as on results.

**Then the same mistake was made one level down, in prose written during the fix.** The behaviour
catalogue's new docstring said "every behaviour here is reached by some check in
`cli/live_storm.py`, and that is enforced rather than intended". It was not: `a-retrieval` and
`d-status` were still driven by nothing, and nothing enforced anything — `FAMILIES` counts
*families*, not behaviours. Found by claim-checking the pass's own documents against the code,
which is the step this repository's rules exist to force ("prose is evidence about what its author
believed, never about what the code does"), and which is worth as much aimed at today's writing as
at last month's.

Both are now driven by checks that assert something real — `d-status` reads the collision's own
job record back through `find_past_jobs`, and `a-retrieval` is what makes family B's
`gather_evidence` and `expand_note` counts about *this* run rather than about rows of unknown age —
and `test_every_declared_behaviour_is_reached_by_some_check` is what keeps the sentence true.

### Family D passed while measuring nothing

> 0 distinct workflow id(s) announced across 12 turns; `calculation_results` 113 → 113 — **PASS**

The bound was `len(launched) <= 1`, which a run that launched nothing also meets. The collision
payload was fixed across runs, so the second storm against one database found it already cached.
`cli/live_jobs.py` documents this failure at length and designs `_RUN_TEMPERATURE_K` against it;
the storm inherited the hazard without the fix.

Fixing it surfaced the harder half: a per-run temperature is not enough, because **the mock is a
separate process** whose catalogue was imported when the lane came up, so the two clocks disagree.
The family now restarts `mock-llm` — which is what actually makes the payload cold — and asks
`job_records` by database timestamp rather than by a workflow id this process cannot know.

### The throughput metric counted refusals as completions

`len(results) / elapsed` scores a shed turn as a drained one. Cap 2 read **6.65 turns/s** with 6 of
48 answering, against **2.45 turns/s** at cap 32 with 32 answering — and the check concluded that
raising the cap *hurt*. Draining a queue by refusing it is fast. Goodput inverts the finding
entirely (see the table above), and both columns are now reported side by side with a line saying
which one is throughput.

### Two checks were wrong about the system rather than the reverse

Worth separating from the vacuous passes, because the correct response is opposite:

- **A 100 KB argument document.** The check demanded a refusal; `find_notes` ran it and returned
  `[]`. A 100 KB search string is legitimate input and surviving it is the right behaviour. Split
  out as `_completed_without_dying`.
- **A new workflow must compute something.** Family D's second check demanded new
  `calculation_results` rows. Measured: one new job record, zero new cache rows — both correct. The
  workflow id hashes the whole payload including `temperature_k`; the cache is keyed on species and
  method. A new temperature is a new *reaction* question answered from cached *species*, which is
  D-011 working one level down — the opposite of the failure the assertion was written to catch.

### Two more, from building the families

- **The chaos worker-kill check proved nothing on its first run.** At `level: "quick"` the benzene
  hydrogenation finished in under four seconds, so the SIGKILL landed on a COMPLETED workflow. The
  check reported that (`at kill: COMPLETED`) and failed itself, which is the property worth having;
  it now polls for RUNNING and kills the instant it is, at `level: "standard"` so there are
  Hessians to interrupt.
- **The disconnect check measured 25.5 s of turn as 25.5 s of lock.** A successful re-POST returns
  an SSE body that only ends when the whole next turn does, and the probe was reading it. Reading
  the status line alone gives the real number: **0.2 s**.

## Mutation testing: 686 mutants over the seven invariant-bearing modules

`make mutants` (`[tool.mutmut]`). Coverage says which lines ran; this says whether anything would
have noticed them being wrong. Before this there were five hand-made mutations from July and
nothing else.

| run | killed | survived | untested |
| --- | ---: | ---: | ---: |
| first | 479 | 130 | 77 |
| after the tests below | **506** | **103** | 77 |

**Three real gaps, each closed by the test the survivor asked for.**

1. **`api/budget.py`** — `counter.tokens += max(tokens, 0)` → `counter.tokens = max(tokens, 0)`
   survived the entire budget suite. Nothing booked two turns and *then* checked a token cap, so
   every test passed against a meter that remembered only the last turn. A token budget that only
   ever sees the newest turn is never reached, which is the exact failure mode of a runaway-cost
   guard that costs money instead of saving it. (`max(tokens, 1)` survived too: no test
   distinguished a free turn from a one-token turn.)
2. **`agent/authz.py`** — `_has_required_role`'s `if not required: return True` → `return False`
   survived. The line is reachable one way only, an operator writing `tool_role_gates: {tool: []}`,
   and nothing exercised it — so a security convention was decided by one unasserted branch. Worth
   pinning because the file states the *opposite* rule two lines away: an empty
   `entra_privileged_role_set` fails **closed**. The asymmetry is deliberate (an operator who wrote
   `[]` has said something; an unfilled chart default has not) but a deliberate asymmetry no test
   can tell from an accident is one refactor away from becoming a security change.
3. **`api/runner_trace.py`** — `hasattr(content, "arguments") or hasattr(content, "call_id")` → `and`
   survived. Under `and`, a function-result content (a `call_id`, no `arguments` attribute) is
   skipped outright: no `tool_result` event, nothing in `outputs`, and so every citation in that
   turn reads as fabricated to the answer verifier. Same species as the defect this module shipped
   the same day — a guard written against a stream shape somebody believed rather than captured.

**Not every survivor is a gap, and saying so is part of the method.** `chain_hash`'s
`chars=_CHAIN_HASH_CHARS` → `chars=None` survived and always will: `_CHAIN_HASH_CHARS` is 64 and a
SHA-256 hex digest is 64 characters, so the mutant is *equivalent*. Most of the remaining
`agent/authz.py` survivors are string mutations on refusal messages (`"XXfooXX"`, `"FOO"`), which
`pytest.raises(match=...)` cannot kill by construction because it searches for a substring. A
mutation score read without that distinction is noise.

**What is left, and where.** 103 survivors, concentrated: `api/runner_trace.py` 37,
`kg/pr_gate.py` 29, `kg/note.py` 16, `science/calc/store.py` 11, `agent/authz.py` 8,
`agent/audit_store.py` 2. That `runner_trace` and `pr_gate` lead is the finding rather than a
coincidence — one shipped a real defect today, the other is the GxP control whose read window this
pass also measured. Recorded in `docs/planning/BACKLOG.md` rather than chased here.

**One scope, not two.** The plan wanted survivors under the whole suite *and* under the narrow
file (DA-7's question: does a narrow run mislead?). Only the narrow scope ran. The reason is
structural: this repository's tests read the *source tree itself* as data — `test_repo_map.py`
walks every directory against `ARCHITECTURE.md`, `test_docstring_paths.py` resolves every
backticked pointer, `test_deploy_chart.py` renders the chart — and mutmut works by copying a
partial tree into `mutants/` and running pytest there. Those tests fail on the copy for reasons
unrelated to any mutant, and none of them could kill one in these seven modules anyway. Stated here
rather than left as an implied "we ran everything".

## Method notes

**Nothing is scored from prose.** Every verdict resolves to an HTTP status, a row count, a Temporal
workflow state, a declared metric, or an event on a stream written to disk — the standing
correction from D-2026-08-03, which matters most here because under load a plausible summary is
the cheapest thing in the system to produce.

**The harness is committed.** The 2026-07 load test's harness was out-of-tree scripts that no
longer exist, so every number in `docs/archive/load-test-2026-07.md` is a rebuild rather than a
replay, and two of its findings were later retracted for exactly that reason.

**Processes are killed and restarted through the lane's own scripts** (`processes.sh restart
<name>`, `bootstrap.sh restart-postgres|stop-temporal|start-temporal`), never by the harness
calling `kill` and `pg_ctl` itself, so a process a recovery check brings back is started exactly as
the lane starts it.

**The chaos family runs last and orders itself by blast radius** — disconnect, worker kill,
database bounce, broker outage — because a family that poisons the ones after it reports their
failures as their own.

**Cost.** A full eight-family run takes ~25 minutes, and about 10 of those are the worker-kill
check waiting out the heartbeat timeout it exists to measure. `--families` narrows a run; the
adversarial and edge families need no volume and complete in under a minute.
