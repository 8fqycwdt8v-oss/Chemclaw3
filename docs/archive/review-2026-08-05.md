# CHECKMATE deep review — the live/durable spine (2026-08-05)

`docs/planning/implementation-plan.md` asks for a deep pass **over the whole code, not the last
diff**, every two phases. The live/durable spine — 4,286 lines across 18 files — had never had one.
This is that pass, over `durable/connector_job.py`, `connectors/jobs.py`, `api/runner*.py`,
`api/routes/*`, `agent/session_store.py`, `kg/pr_gate.py` and `kg/git_submitter.py`.

Two rules shaped what it spent its budget on:

- **It did not re-review what a test already proves.** G6 (layer purity) is machine-proven by
  `tests/test_layering.py`'s AST import graph, the ADR ledger by `tests/test_decision_log.py`, the
  repo map by `tests/test_repo_map.py`. The review audited those *policy constants* and went looking
  where nothing was looking.
- **Nothing was written down before it was reproduced.** Every finding below carries a `file:line`,
  a measured number and the command that produces it. Three candidate findings died at that step and
  are not here.

The method that found most of it was mutation: delete the guard, run the tests it is named after,
see whether anything notices. **Eight guards over this spine could be deleted with the suite green.**

## Findings, by severity

### 1 · The mid-turn resume spent tokens nobody metered — `api/runner.py:741`

The resume drives a **second** `agent.run`. Its usage never reached `usage_tokens`, so none of it
reached the budget guard, `chemclaw_tokens_total` or the `TurnCost` row.

Measured on a turn that spent 1,000 tokens before the wait and 5,000 after it: **the ledger booked
1,000.** 83 % of the turn's spend was invisible, and the one feature that adds an *unbounded* second
model call was the one feature D-144's runaway-cost refusal could not see.

Fixed: `_resume` takes the turn's `TurnUsage` and adds to it.
Pinned: `tests/test_review_2026_08_05.py::test_the_mid_turn_resume_meters_its_own_tokens` — verified
to fail when the accumulation is removed.

### 2 · A re-joined job that fails reaches the model wordless — `connectors/jobs.py:398`

Two branches await a workflow result inside a turn. The freshly-started branch framed
`WorkflowFailureError` as a `ConnectorJobError` carrying the run's own reason; the **re-joined**
branch — a second chemist asking for a job already running — did not. `WorkflowFailureError` is
neither a `ChemclawError` nor a `SubsystemUnavailableError`, so `surface_domain_errors` passes it
through and MAF renders "Error: Function failed."

That is the fourth appearance of one defect, and its history is the argument for the fix chosen. The
first made a model fabricate a whole development report when the broker was unreachable; the second
was the launch that could not be confirmed; the third was this same framing, added at one call site
on 2026-08-04. **Copying the guard to the second call site would have set up the fifth.** The framing
now lives inside `_await_briefly` — the only function that awaits — so a third caller cannot forget
it, and `test_both_awaits_go_through_the_framing_function` asks the module's AST whether anyone
awaits a result outside it.

### 3 · Compaction could delete the turn that triggered it — `agent/session_store.py:370`

`save_messages` protects the rows it just inserted from the compaction it just triggered, by
watermark. `plan_compaction`'s `protected` parameter is tested directly; **the call site's
derivation of it was not.** Replacing it with `protected=set()` left 31 tests green across all three
files that name compaction.

Measured against a real database with `agent_durable_compaction_min_rows=4` and
`agent_context_token_budget=50`: **rows after = 0, the new turn survived = False.** A conversation
that answers and then forgets the exchange it just had is the worst failure this store has.

Pinned: `test_compaction_never_deletes_the_turn_that_triggered_it`, verified to fail against
`protected=set()` on live Postgres.

### 4 · Every calc job started without being counted — `connectors/jobs.py:453`

`chemclaw_jobs_started_total` was incremented *after* the inline wait, and a job that answers inside
the turn returns before reaching it. **Five of the seven declared jobs carry `inline_wait_seconds`**
— every `calc` job — so the counter an operator reads as "durable work launched" systematically
missed the common case, while `chemclaw_job_runtime_seconds_total` (booked from the job record,
which is written either way) kept counting their runtime. Starts and runtime were read off one
dashboard and only one of them was true.

Fixed: counted immediately after `start_workflow` returns, which is when a workflow has started.
The re-joined path still counts nothing, correctly — it starts nothing.

### 5 · D-011's idempotency contract was asserted by nobody — `connectors/jobs.py:391`

Four launch sites pass `ALLOW_DUPLICATE_FAILED_ONLY`, and every mention of it under `tests/` was
**prose in a docstring**. Changing the connector-job launcher to `ALLOW_DUPLICATE` — which silently
recomputes a *completed* job, the exact thing D-011 exists to forbid — left **447 tests green**.

Pinned: `test_every_durable_launch_keeps_the_failed_only_reuse_policy` reads the reuse policy out of
the AST at all three launcher modules.

### 6 · `failure_reason` had no test that runs offline — `durable/connector_job.py:62`

A pure function, 34 lines of docstring arguing which frame to pick, corrected by a live incident
within the hour of shipping. Its only coverage needed a Temporal server and **skips in every offline
run**, so lines 87–90 were unexecuted. Reverting the walk to the innermost frame — the version
`D-2026-08-04` corrected — left **458 tests green**.

Now covered by three direct tests, including the one the incident produced: the chemist gets
"unknown ALPB solvent '2-methyltetrahydrofuran'", not the tblite internals one frame below it.

### 7 · The trace's empty-fragment guard was untested — `api/runner_trace.py:125`

The guard's own comment records that it "reached a second live run still empty". Replacing
`if arguments is None:` with `if not arguments:` kept **160 tests green**: the existing test places
the empty fragment *before* any accumulation, where both spellings agree. Placed mid-document it is
the storm's defect again — `{"smi` announced as a whole call, then `les": "CCO"}` as a second one.

### 8 · The turn's closing flush was untested through a turn — `api/runner.py:353`

`ToolCallTrace.flush()` is tested on the object. Deleting `run_turn`'s call to it left **160 tests
green**, and a call whose arguments never parse as JSON — a provider that streams something other
than JSON — vanishes from the stream entirely without it.

### 9 · A test I wrote last pass pinned nothing — `tests/test_pr_gate_read_window.py:183`

`test_readers_are_not_synchronised_with_the_submitter` named a real mechanism and asserted
`count >= 1` and `graph_cache_ttl_seconds >= 0` — both true under **every** implementation, including
the fixed one. It would have passed the day a reader lock was added, which is the behaviour it
claims to pin. In a file written to stop exactly this.

Replaced with a read taken *while* `_checkout_lock` is held, which is the assertion that inverts on
the day the fix lands.

## Recorded, deliberately not fixed

Each needs a decision rather than a diff, and the diff does not widen quietly:

- **A crash mid-submission leaves the shared checkout on `note/<id>`** with the unreviewed note in
  the tree, and nothing in the application repairs it — no startup reconciliation, no test. Measured
  with a real git remote and a SIGKILLed child: `branch after SIGKILL: note/job-crash`, and
  `load_notes` returns it. Bounded only by the deployment sidecar's `rsync --delete` (300 s), and
  **unbounded** in the `infra/live/` topology. Same family as the read window, and the same fix
  (`git worktree` for the submission) closes both — which is why it should be taken once, as a GxP
  architecture decision.
- **A `FAILED` proposal for a multi-file submission cannot be replayed.** `NoteProposal.content`
  keeps only `files[0]`, so the dependency bytes are gone and the replayed note's `[[wikilink]]`
  would dangle — the failure `NoteSubmission`'s multi-file design exists to prevent. Measured: a
  two-file submission stored 131 chars, dependency body absent. 4 of 9 `propose_note` call sites
  pass dependencies.
- **`pr_gate._REASON_CHARS = 300` does not do what it says.** Its comment justifies the bound as
  keeping "a token-bearing remote URL" out of the compliance table; a realistic credential-bearing
  git failure measures **235 chars**, so it is stored verbatim, and the path bypasses the
  `core/logging` redaction inventory entirely. Redaction, not truncation, is the fix.
- **`SessionTurnClaims.refresh` discards `cur.rowcount`**, so a holder whose lease was stolen cannot
  detect it; `_hold_turn_claim`'s own warning ("another worker may start a turn on this session") is
  unreachable in exactly the scenario it describes.
- **Two `PlanEvent` emit sites with different predicates** (`runner.py:340` vs `:390`); the
  post-resume one can emit the empty checklist the other's docstring says must never be produced.
- The webhook contract (false claim 6) and the layering policy's granularity (G6).

## The soak: what drifts when nothing is disturbed

A separate question from the storm's, and it needed a run long enough to answer. `infra/live/soak.sh`
repeats families `BCDFGH` — not A or E, which restart the front door and SIGKILL a worker, so the
RSS of a process that has just been replaced is not a series — checkpointing each round to
`.live/soak.jsonl`, resuming from the record when the container comes back.

**The verdict changed four times as the run got longer, and that is the finding.** The same series,
the same process, nothing about the system changing:

| after | reading | verdict |
| ---: | --- | --- |
| 29 rounds | `+4,690 KB/round (± 764)`, tail `+6,896` | resolved, *accelerating* — one step from a filed memory leak |
| 43 rounds | `+3,597 KB/round`, tail unresolved over 22 rounds | *rises then settles* — a plateau |
| 104 rounds | `+2,317 KB/round (± 200)`, tail `+1,345` | *decelerating* — growth that is running out |
| 138 rounds | first half `+3,166`, second half `+3,177`, last quarter `+5,138` | **steady** |
| 162 rounds | first half `+2,666`, second half `+3,864`, last quarter `+4,363` | **steepening** |

Every one of those fits was *resolved*, with a tight error bar. Three of the five were wrong, and
the two that agree are the two that compared equal-length windows.

**The last two are right, and the first three were wrong for one identifiable reason:** the comparison
was between the tail and the *whole*, and the whole contains the tail. On a series that rises in
steps — which this one does; round 40 returned 134 MB in a single step, as allocator arenas do — an
early flat stretch drags the whole-run slope below the tail's, and "tail below whole" then reads as
deceleration when nothing decelerated. Two equal-length independent windows can be compared; a window
and its own superset cannot. `describe()` now compares halves, and `D-2026-08-05-a-trend-needs-a-tail`
carries the correction.

**So the finding is that api RSS grows without bound under sustained load**: 549 MB → **1,066 MB**
across the full 162 rounds (~2 h 40 m), with the halves at `+2,666` and `+3,864 KB/round` (± 219)
and the last quarter at `+4,363` — **steepening** at every window examined, ~47 KB retained per turn
at the closing rate. The run ended because it was stopped, not because it plateaued.
`chemclaw_live_sessions` sat pinned at its `service_max_live_sessions` bound of 1000 throughout, so
it was never the LRU filling; row counts grow exactly linearly, the pool never waits, and round
wall-clock is flat or falling. On OpenShift this is a pod that OOMs on a timer.

**It is a BACKLOG row rather than a fix**, because finding *what* is retained needs an allocator-level
look (`tracemalloc`, `malloc_stats`) that a soak cannot give — but it is no longer a question of
whether there is something to find.

**The soak also found an intermittent nothing else could.** Family D failed in 6 of 81 rounds with
"0 job_records row(s) written", spaced ~12 rounds apart. Nothing was broken: the collision payload's
per-run temperature had a **719-second period**, so a value recurred every ~12 minutes, and
`ALLOW_DUPLICATE_FAILED_ONLY` correctly rejoined the already-completed run instead of recomputing it.
D-011 working, read as a failure — the third time this family's *measurement* has been wrong, and the
first that a single storm could never have shown. The period is now 27 hours, and the 23 rounds run
since carry **zero** such failures against the ~2 the old period predicts — supportive rather than
conclusive, and stated that way.

The RSS verdict held its shape once the run was long enough to have one: at 104 rounds it reads
`+2,317 KB/round (± 200), still +1,345 over the tail`, the same story as 81 with a tighter error
bar. Two consecutive readings agreeing is the first thing this series has done that the earlier
ones did not.

`chemclaw.cli.soak_report` is why each correction happened rather than each mistake: it reports a
slope **with its standard error**, refuses to name one inside its own error, and separates "the tail
is flat" from "the tail is too short to fit" — two verdicts the first draft collapsed into one. The
scratch soak that preceded it had five points and reported the difference between its endpoints.

The lesson `D-2026-08-05-a-trend-needs-a-tail` records is therefore stronger than when it was
written: a tail long enough to *fit* is not the same as a run long enough to *conclude*. At 43 rounds
the tail was fittable and said "flat"; at 81 it says "+1,238". The rule that survives is to report
what the current length supports and to say so — never to convert a fit into a verdict about the
system.

## The `make ci` question, answered with the number

Should a fast storm subset run on a diff? **No.** The adversarial families F, G and H take **31 s**
against a running stack, 14/14 — fast enough to be tempting. The cost is not the checks, it is the
stack: CI has Postgres and **no Temporal at all**, which is why two durable tests already skip there.
A subset on a diff would mean either standing up a broker per PR or running one that silently skips
its durable half — and a green check that skips what it names is precisely what this pass exists to
remove. `make live-storm` and `make live-soak` stay out of `make ci`, run against a deployment.

## Postscript: the [H] leak, named — and a comment that broke migrations everywhere

**The leak had a cause, and it was not the shape the soak suggested.** "Steepening" reads as an
unbounded structure filling. `chemclaw.cli.leak_probe` (`make leak-probe`) drives the same turns
*inside* the measuring process, where `gc` and `tracemalloc` can see what a soak cannot, and the
answer was that `configure_telemetry()` **returned early**: with no meter provider set, the
OpenTelemetry API does not discard instrument calls, it *proxies* them and retains every proxy
forever. MAF creates a duration histogram per exposed MCP function, and this system rebuilds its
connector tool surface every turn, so each turn leaked 35 `_ProxyMeter`s, 35 `_ProxyHistogram`s, 70
locks and 35 lists.

| | before | after |
| --- | ---: | ---: |
| RSS per turn | +20.7 KB | **+2.7 KB** |
| live objects per turn | +178.2 | **+3.3** |

Two methods agreed — a gc type histogram named the types, `tracemalloc` named the allocation lines
— and the fix is one call: install `NoOpMeterProvider` when telemetry is off. **The hypothesis going
in was refuted rather than confirmed**: MAF re-entering unconnected tools into the agent's
process-lifetime exit stack was plausible and documented in this repo's own docstring, and the probe
measured that count flat at zero across 200 turns. Killing the plausible explanation before building
on it is what left the search pointed where the answer was. The test that pinned this asserted the
defect — `test_configure_telemetry_is_a_noop_when_disabled` said disabled telemetry "does nothing",
which was true and was the bug.

**And the work ran into a defect on `main` that CI could not see.** A comment-only edit to an
already-applied migration (`031_bo_campaigns.sql`) broke `make db-migrate` on every database that
had applied it, because the drift guard hashed the whole file; CI always starts from an empty
database, so it stayed green. It was the *second* such edit — `006_audit_events.sql` had been
failing the same way for four days. The guard now hashes the statements, a ledger row written under
the old rule is recognised once and rewritten, and a test asks git the same question the runner asks
the ledger, using the runner's own reduction so the two cannot disagree.

Eight behavioural mutants were also killed in the two files holding two thirds of the survivors,
three of them only after the first attempt failed to kill its own mutant — a loop test that put the
duplicate last, a cap test asserting a length identical under both bounds, and one written against a
premise the code does not have.
